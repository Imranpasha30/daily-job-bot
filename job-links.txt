--- Python / SQL data pipeline and scale ---
At Sharkify I built the backend for Voter Connect, a campaign platform running on a 9.9 million row PostgreSQL dataset. The pipeline ingested and normalised voter rolls, and reads had to stay under a second for field volunteers on mobile. I got there with composite indexes designed off EXPLAIN ANALYZE query plans, rewritten aggregate queries, and Redis caching on the hot lookup paths.

On Kaizer X I own a multi-stage Python pipeline that moves video through transcription, LLM-driven edit decisions and FFmpeg rendering. Stages are coordinated by a durable PostgreSQL job queue using FOR UPDATE SKIP LOCKED with lease fencing and exponential backoff, plus a Redis Streams consumer-group queue with XCLAIM crash recovery and a dead-letter stream for fan-out across workers.

I work in Python and SQL directly rather than PySpark. My scale is tens of millions of rows and multi-gigabyte media objects, not petabyte Spark workloads.

--- AWS experience (S3, EC2, Lambda, EKS, MSK) ---
S3: hands-on and heavy. At Bose American Academy I migrated object storage from AWS SDK v2 to v3, with dynamic per-user and per-course key paths, delete-on-replace for profile images and guaranteed temp-file cleanup when an upload failed. On Kaizer X and Ozone Wash I built the storage layer against the same S3 API using boto3 and the AWS SDK, with presigned URLs, environment-prefixed key namespaces and a local fallback. That layer also resolved a production disk-fill outage by deleting local copies once the object store confirmed the upload.

EC2: KaizerFit and the Bose API both deploy to EC2 as Docker containers through GitHub Actions, writing env from secrets, rebuilding the image and replacing the running container behind NGINX.

Lambda: I prototyped Lambda handlers for username and email availability checks and OTP dispatch on KaizerFit, then folded them back into the FastAPI service to reduce operational surface.

EKS and MSK: I have not run either in production. My container work is Docker and Compose rather than managed Kubernetes. For streaming I used Redis Streams with consumer groups, pending-entry recovery and a dead-letter stream, which is the same consumer-group model as Kafka and MSK, but not the managed AWS service.

--- Biggest production incident you solved ---
A Redis upload stream on Kaizer X grew from 8 entries to over 619,000 at roughly 80 enqueues per second. I traced it to a time-of-check-to-time-of-use race between two worker paths reading job status and a re-enqueue loop with no backoff. I replaced the status check with an atomic conditional UPDATE claim and removed the loop; the stream then held steady at one message. I wrote a regression test that reproduces the race before shipping the fix.

--- Security experience relevant to backend ---
I hold an Executive Post Graduate Certification in Cyber Security and Ethical Hacking from IIT Roorkee's iHUB DivyaSampark. I apply it to API design rather than keeping it separate: I closed a two-round adversarial security review on Kaizer X with a regression test behind every fix, covering cross-tenant authorization (BOLA and IDOR) on live-broadcast controls and WebSockets, an OAuth callback XSS, and password-reset links that trusted an attacker-controlled Origin header. I also wrote an SSRF guard that resolves DNS before refusing loopback, private, link-local and cloud-metadata addresses, and replaced client-declared MIME types with byte-level magic-number verification.
